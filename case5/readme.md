# Анализ качества веб-сервиса «Новогодний калькулятор»

В качестве объекта исследования взята четвёртая кейс-задача — веб-сервис «Новогодний калькулятор», который вычисляет, сколько дней осталось до наступления Нового года, а также определяет, является ли указанный пользователем год високосным.

---

## Оценка по критериям качества

### 1. Функциональная полнота

Приложение успешно справляется с основной задачей: разбирает введённую дату, вычисляет разницу в днях до 31 декабря и корректно проверяет високосность года по стандартному алгоритму (деление на 4, исключение столетий, кроме кратных 400).

**Обнаруженные недостатки:**

- Конструктор `new Date(year, month - 1, day)` в JavaScript молчаливо корректирует невалидные даты: так, `31.02.2026` тихо превращается в `03.03.2026`, и стандартная проверка через `isNaN(date.getTime())` не фиксирует ошибку.
- До момента создания объекта `Date` не контролируются допустимые границы дня (1–31) и месяца (1–12).
- Не обрабатываются ситуации с пустым вводом или буквенными символами внутри фрагментов даты (к примеру, `аб.06.2026` даст `NaN` и сообщение «Некорректная дата», однако причина ошибки пользователю не поясняется).

**Как исправить:**

- Ввести предварительную ручную проверку диапазонов (день 1–31, месяц 1–12) с учётом реального числа дней в конкретном месяце и високосности.
- Применить регулярное выражение для контроля формата строки ещё до парсинга, например `/^\d{2}\.\d{2}\.\d{4}$/`.

---

### 2. Быстродействие

Все вычисления строятся на объектах `Date` и простых арифметических операциях с миллисекундами, что выполняется практически мгновенно и не зависит от объёма входных данных. При однократном нажатии кнопки быстродействие не является слабым звеном.

> **Заключение:** данный критерий не играет существенной роли для этой задачи, поскольку вычислительная сложность составляет `O(1)`.

---

### 3. Эргономика и удобство интерфейса

**Обнаруженные недостатки:**

- Тексты ошибок («Неверный формат даты», «Некорректная дата») слишком общие и не подсказывают пользователю, что конкретно нужно поправить.
- Поле ввода лишено маски и автоматического форматирования (например, автоподстановки точек при наборе цифр).
- Нет визуальной обратной связи об ошибке (к примеру, красной обводки поля).
- Форму нельзя отправить клавишей `Enter` — расчёт запускается исключительно кликом по кнопке.

**Как исправить:**

- Формулировать ошибки конкретнее, например: «Укажите день в диапазоне от 1 до 31».
- Внедрить маску ввода на JavaScript (автоподстановка разделителей) либо заменить поле на `type="date"`, дающее встроенный календарь и браузерную валидацию.
- Повесить обработчик `keydown`, чтобы расчёт стартовал по нажатию `Enter`.
- Подсвечивать проблемные поля через CSS-класс (например, `border: 1px solid red`).

---

### 4. Защищённость

Сервис не оперирует персональными данными и не обменивается информацией с сервером, поэтому угрозы утечки отсутствуют.

**Обнаруженные особенности:**

- Для вывода результатов используется `textContent`, а не `innerHTML`, что надёжно предотвращает XSS-атаки — это безусловный плюс текущей реализации.
- Поскольку вся логика работает исключительно на стороне клиента, значимых уязвимостей в рамках существующего функционала не обнаружено.

> **Заключение:** для локального приложения безопасность не является приоритетом, однако при масштабировании до серверного решения потребуется дублировать валидацию на бэкенде.

---

### 5. Возможность масштабирования

**Обнаруженные недостатки:**

- Вся логика сосредоточена в единственной функции `calculate()`, что создаёт трудности при добавлении новых возможностей (например, подсчёта дней до других праздников) без копирования кода.
- Жёстко зашитые идентификаторы DOM-элементов (`dateInput`, `result1`, `result2`) мешают многократному размещению компонента на одной странице.

**Как исправить:**

- Декомпозировать `calculate()` на отдельные функции: `parseDate()`, `calculateDaysToNewYear()`, `isLeapYear()`, `renderResult()` — каждая отвечает за одну задачу (принцип единственной ответственности, SRP).
- Вынести логику в самостоятельный модуль (отдельный `.js`-файл), отвязав её от HTML-разметки.

---

### 6. Лёгкость сопровождения

**Обнаруженные недостатки:**

- Код не содержит комментариев, поясняющих логику блоков и формулу определения високосности.
- Нет единообразного стиля именования переменных; константы не выделены (встречаются «магические числа»: `11` для декабря, `1000 * 60 * 60 * 24` для пересчёта миллисекунд в сутки).
- HTML, CSS и JS объединены в одном файле, что затрудняет поддержку по мере роста проекта.

**Как исправить:**

- Оформить JSDoc-комментарии к функциям с указанием параметров и возвращаемых значений.
- Заменить «магические числа» именованными константами (например, `const MS_IN_DAY = 1000 * 60 * 60 * 24`).
- Разнести код по трём файлам: `index.html`, `style.css`, `script.js`.

---

### 7. Кроссплатформенность

Приложение построено на стандартных веб-технологиях (HTML, CSS, чистый JavaScript) без внешних библиотек и серверных зависимостей, что гарантирует высокую переносимость — страница корректно откроется в любом актуальном браузере на любой операционной системе.

**Обнаруженный недостаток:** не проводилась проверка кроссбраузерной совместимости (в частности, поведение конструктора `Date` на граничных значениях может незначительно различаться в разных движках).

**Как исправить:** протестировать приложение в нескольких браузерах (Chrome, Firefox, Safari) и при необходимости заменить ручной парсинг на встроенный `<input type="date">`, унифицирующий поведение на уровне браузера.

---

### 8. Чистота и качество кода

**Обнаруженные недостатки:**

- Наблюдается рассогласование имён классов: в HTML используется `result-box`, а в CSS — `result`, из-за чего стили из `.result` фактически не применяются к блокам с классом `result-box`.
- Не проработан сценарий ввода одиночных цифр (например, `5.6.2026` вместо `05.06.2026`): хотя `Number()` их корректно распознаёт, этот случай не был явно учтён и протестирован.

**Как исправить:**

- Синхронизировать имена CSS-классов с атрибутами в HTML.
- Провести рефакторинг с распределением ответственности по функциям (см. раздел «Масштабируемость»).
- Активировать строгий режим (`'use strict'`) и подключить линтер (например, ESLint) для автоматического обнаружения подобных расхождений.

---

### 9. Покрытие тестами

**Обнаруженные недостатки:**

- Автоматизированные тесты полностью отсутствуют — вся верификация проводилась вручную через интерфейс браузера.
- Тестовые сценарии не задокументированы ни в отдельном файле, ни в рамках какого-либо фреймворка модульного тестирования.

**Как исправить:**

- Преобразовать `isLeapYear()` и `calculateDaysToNewYear()` в чистые функции без побочных эффектов (без обращения к DOM), что сделает их пригодными для автотестирования.
- Написать модульные тесты с применением фреймворка (например, Jest), покрыв граничные случаи: несуществующие даты, переход через границу года, секулярные високосные годы (1900, 2000).

## Общее заключение

Проведённая оценка показывает, что приложение полноценно решает заявленную функциональную задачу, однако имеет ряд слабых мест в эргономике, архитектуре кода и тестируемости, характерных для учебного прототипа. Все предложенные улучшения не предполагают пересмотра архитектуры и могут внедряться итеративно без ущерба для существующего функционала.
